## 후기 첫 요청·홍보 근거 검증 · 2026-11-19

새 평가용 OpenAI 키로 **후기 첫 요청 3/3, 세 채널 홍보 생성 3/3**을 실제 검증했습니다. 더애월 본점·김치찌개·`2021-06-01`을 같은 조건으로 요청했고, 매번 `2021-02-14` 공개 후기 1건과 해당 메뉴의 포인트 1개가 반환됐습니다. Agent 결과 캐시나 저장된 검색 응답을 사용하지 않았습니다. 후기 요청은 각각 **13.610 / 14.732 / 9.784초**, 세 채널 생성은 **4.698 / 4.643 / 4.606초**였습니다. 별도 AI 질문에서 김치찌개610→462·오후2~5시208→104와 출처, 한국어 테스트 WAV의 전체 문장 전사도 실제 호출로 확인했습니다. 이 음성 검증은 새 실제 아이폰 마이크 조작 검증을 뜻하지 않습니다.

후기는 본점 같은 접미사를 정리한 상호·도로명·선택 메뉴·기준 연도로 검색합니다. 결과가 비거나 원문 확인에 실패하면 같은 요청 안에서 주소 검색어를 완화해 한 번 더 검색하되, 원문에서의 매장·주소·기간 검증은 유지합니다. 날짜와 인용문을 AI가 다시 쓰게 하지 않고 **서버가 잘라낸 메뉴별 원문 구절의 번호만 선택**하게 했습니다. 같은 날짜의 표기·0 채움 차이는 허용하지만 실제 오늘을 기준으로 한 상대 날짜와 과거 기준일은 구분합니다. 새 글에 달린 예전 관련 글 날짜는 사용하지 않습니다. 메뉴 목록·수량 안내·관련 글·다른 메뉴 평가는 후보에서 제외합니다. 모델이 빈 선택이나 빈 포인트를 반환하면, 날짜·매장·메뉴·평가 표현이 확인되고 광고 고지가 없는 개인 후기의 짧은 실제 구절만 확인 포인트로 유지할 수 있습니다. 자료가 없을 때 내용을 만들어 채우지 않습니다.

사진은 미리보기·홍보 이미지용으로 유지하며 **문구 생성 모델에는 사실 근거로 보내지 않습니다.** 세 채널 초안은 확인된 메뉴·매장 사실과 선택 후기 포인트만 사용합니다. 생성 후 문장별로 근거 ID를 대조해 재료·조리·제공 방식 등이 뒷받침되지 않으면 제외하고, 단순 권유 말투로 사실 검증을 우회하지 못하게 했습니다. 반복 생성한 9개 채널 본문에서 선택 포인트가 유지됐고, 선택 원문에 없던 두부·파·뚝배기·밥/반찬 제공·토핑·포장 안내가 없음을 확인했습니다. 짧은 근거에 맞춰 글이 짧아질 수 있으며 실제 게시 전 검토가 필요합니다.

이전 검증 형식의 후기 검색과 빈 포인트 결과는 재사용하지 않습니다. 기존 자동 초안의 검증 버전도 구분하며 사용자가 직접 수정한 초안은 보존합니다. 배포 후에는 화면을 새로고침하고 **이 메뉴 후기 찾기 → 포인트 선택 → 세 채널 초안 만들기** 순서로 다시 확인합니다. 외부 검색·원문·모델 응답의 가용성이 모든 요청에서 보장된다는 뜻은 아닙니다. 실제 키는 로컬 전용 파일에서 읽어 검증 프로세스에만 전달했고 콘솔·검증 산출물·Git에는 넣지 않았습니다.

## Railway 서비스 주소 변경 · 2026-11-18

프로젝트는 `jeju-shop-buddy`, Web은 `shop-buddy-web`, Agent는 `shop-buddy-agent`로 이름을 정리했습니다. 공개 주소는 **https://gage-jjakkung.up.railway.app/**입니다. 기존 서비스·DB를 유지했으며 세 서비스가 Online이고, Web의 `STRATEGY_AGENT_URL`이 `http://${{shop-buddy-agent.RAILWAY_PRIVATE_DOMAIN}}:8001`을 참조하는 것을 확인했습니다. 내부 DNS는 기존 연결을 유지하며 서비스 표시 이름에서 주소를 추측해 바꾸지 않았습니다.

새 HTTPS 주소에서 기존 시연 계정 로그인, 더애월 매장·저장 분석·시연 기준일 유지, AI 질문 응답을 확인했습니다. 메뉴 이름 없이 물었을 때 김치찌개 **610→462개**, 오후 2~5시 결제 **208→104건**과 근거 4개가 반환됐습니다. 공개 메뉴판은 기존 ID를 유지하고 새 호스트의 `/menu/{공개 ID}`로 QR이 생성됩니다. 인증 없는 공개 API 요청이 HTTP 200이며 메뉴 5개·사진 5개가 유지됐고, 브라우저에서 네 언어 전환·김치찌개 8,000원과 390×844 크기에서 가로 넘침 없음을 확인했습니다. 새 주소의 배포 설정·시연 문서 링크를 맞췄으며 실제 아이폰 기기 재검증을 뜻하지 않습니다.

새 주소에서는 다시 로그인하고 **내 매장 → 다국어 QR 메뉴판**에서 새 QR을 사용합니다. 이미 저장·인쇄한 옛 QR 이미지는 주소를 자동 변경할 수 없으므로 교체해야 합니다.

## 홈에서 보는 기능 흐름

매출 분석부터 실행 결과까지 **여섯 단계를 각각 한 화면 높이(`100svh`)**로 구성했습니다. PC에서는 설명과 애니메이션을 나란히 배치하고, 화면 너비·높이와 그림의 실제 크기에 따라 제목·그림 배율을 조절합니다. 모바일에서는 핵심 제목과 그림을 먼저 보여주고 **기능 설명·자료 안내**를 펼쳐 부연 설명과 원문 링크를 확인합니다. 설명을 펼치거나 화면 높이가 매우 짧으면 잘리지 않도록 단계 높이가 늘어납니다. 로컬 프로덕션 빌드의 1280×720·1920×1080 PC, 820×1180 태블릿, 390×844·390×667 모바일 크기에서 여섯 단계가 각각 화면 높이에 맞고 가로 넘침이 없음을 확인했습니다. 390×500에서는 내용을 보존하며 높이가 늘어납니다. 세 채널 카드 펼치기·사진 로딩, 모바일 설명 펼치기·접기와 QR 예시 영어·일본어 직접 전환도 확인했습니다. 짧은 모바일 화면의 언어 버튼은 배율 적용 후에도 높이 44px 이상입니다. 프런트엔드 빌드와 `npm run verify:home`이 통과했으며 실제 아이폰 기기 검증을 뜻하지 않습니다.

주요 기능 도입부는 가로 전체·최소 한 화면 높이의 짙은 초록색 배경과 밝은 글자로 표시합니다. `100svh`를 기준으로 내용을 세로 중앙에 배치하고, 내용이 화면보다 길면 높이를 늘려 잘리지 않게 합니다. 제목은 화면 너비·높이에 맞춰 크게 조절하고 본문·바로가기·자료 안내·움직임 옵션을 가운데 정렬합니다. PC 720px 높이에서 제목 약 94px, 390px 너비 모바일에서 약 45px이며 글자·버튼 잘림과 가로 넘침 없음을 확인했습니다. PC 720px·390px 너비 모바일 844px에서 화면 높이와 일치하고, 높이 500px에서는 내용에 맞춰 늘어나며 버튼과 가로 넘침이 없음을 확인했습니다. 제목은 **매출 분석부터 발주·홍보까지.**로 바꾸고 기능 소개·마지막 시작 안내를 짧고 구체적인 문장으로 정리했습니다. [토스플레이스 기능 안내](https://tossplace.com/story/salesreport_detailed_analysis)와 [캐시노트 홈페이지](https://cashnote.kr/)의 기능 설명 방식을 참고했으며 문구를 그대로 옮기지 않았습니다. 실제·가상 시연 자료 안내는 별도로 유지합니다. 프런트엔드 빌드·홈 집계 검증과 PC·390px 배치·가로 넘침 없음을 확인했습니다.

홈의 제주 가게 배경·고민 말풍선 다음을 **매출·상권 비교 → AI 감소 근거 → 하루 발주 검토 → 세 채널 홍보 → 다국어 QR → 실행 결과** 순서로 구성했습니다. 예전 고기국수 할인·주문 안내·다른 기간의 성과 예시는 홈에서 제거했습니다. 로그인 없이 읽는 고정된 기능 소개이며 방문자의 계정·매장·분석을 조회하거나 실제 AI 호출·게시·결과 저장을 실행하지 않습니다.

스크롤하면 POS·공공자료 카드와 매출 그래프가 나타나고, 질문·답변·근거 카드, 발주 계산 단계, 세 채널 홍보 카드 펼치기, QR 스캔선·휴대폰 등장·번역 전환, 예상 범위·기록 판매와 전후 막대 비교가 이어집니다. 상단의 6개 바로가기로 원하는 장면에 이동할 수 있고 **움직임 효과**를 끌 수 있습니다. 기기의 움직임 줄이기도 기본 반영합니다. 언어 예시는 보이는 동안 네 언어를 한 번 순서대로 보여주며 직접 누르면 자동 전환을 멈춥니다.

2021년 더애월 공개정보를 참고한 사례이며 **실제 상권·공개 후기·당시 전시 출처**, **가상 POS·재고·원가·실행 결과**, **AI 예시 사진·번역**을 구분합니다. 홈의 QR은 `/#landing-menu-preview`의 홈 메뉴판 예시로 연결되며 실제 고객용 공개 메뉴판 QR과 구분합니다. 김치찌개 AI 사진은 이 프로젝트에서 2026-11-18에 제작했던 예시를 재사용하며 실제 식당 사진이 아닙니다. 정상가 8,000원, 발주 예상 20~24인분·돼지고기 0.5~0.9kg, 가상 결과 23인분·204→247·48→72건을 사용합니다. 메뉴 감소와 시간대 감소는 각각의 집계이며, 전후 변화는 실제 매장 성과나 홍보의 인과 효과를 뜻하지 않습니다.

검증: `npm run build`, `npm run verify:home`, 기존 `npm run verify:overview`가 통과했습니다. 홈 수치를 독립된 4·5월·실행 후 시연 예상 집계 JSON과 대조했고 돼지고기 사용량·재고·입고 예정량 계산과 6단계 순서를 확인했습니다. 로컬 프로덕션 빌드에서 PC의 그래프·카드 이동, 사진 로딩, 390px 가로 넘침 없음, 네 언어 직접 전환과 움직임 끄기를 확인했습니다. 실제 아이폰에서 새 홈을 검증한 기록은 포함하지 않습니다.

## 우리 가게 대응 한눈에 보기

로그인 후 저장된 분석을 선택하고 사이드바의 **대응 한눈에 보기**를 누릅니다. 매출 분석 하단과 실행 관리·결과 확인 상단에서도 같은 분석의 `/overview?id=분석ID`로 이동합니다. **감소 발견 → 대응 준비 → 결과 확인**을 한 화면에서 연결하며 매출 분석·AI 전략·발주 검토·홍보 초안·실행 기록으로 돌아갈 수 있습니다. 기존 기록을 조회하며 새 분석·AI 호출·게시·결과 저장을 실행하지 않습니다.

- 근거: 동일 기간·지역·업종 카드 이용액과 매장 매출 증감률, 저장된 상품 매출 감소액이 가장 큰 메뉴, 감소한 시간대입니다. 메뉴별 감소와 시간대별 감소는 각각의 집계로, 메뉴×시간대 교차 분석으로 표현하지 않습니다. 세부 업종 비교 자료가 없으면 직접 비교하지 않고 참고 범위를 별도로 표시합니다.
- 대응: 이 분석에 저장된 발주·홍보 계획만 연결합니다. 계획이 여러 개면 선택할 수 있고, 선택한 계획의 초안·결과만 함께 바뀝니다. 발주 예상은 현재 계획·결과 날짜·메뉴가 모두 일치해야 비교합니다. 예정된 날짜의 저장 예상은 준비 단계에서 볼 수 있고, 실행 결과는 서버의 시연 기준일 제한을 따릅니다.
- 자료 구분: 상권 공개자료와 출처, 가상 POS, 가상 실행 결과를 별도로 표시합니다. 분석의 가상 표시는 체험 데이터 또는 분석 이름의 `가상`·`SIMULATED` 표시에 근거합니다. 일반 분석은 실제/가상 여부를 임의로 판단하지 않고 **매장 입력 · 실제/가상 미확인**으로 표시합니다. 실행 결과는 서버에 저장된 자료 구분을 따릅니다. 공개 후기·행사 원문, 추천 근거, 결과 CSV 파일명·SHA-256은 접어서 확인합니다. 초안 저장은 실제 게시 완료가 아니며 가상 결과와 전후 변화는 실제 매장 개선 효과의 증거가 아닙니다.

## 실행 기록과 가상 후속 결과

사이드바의 **실행 관리**는 계정에 저장한 계획 목록을 서버에서 불러옵니다. 새로고침·재로그인·시연 기준일 변경 후에도 계획을 다시 선택할 수 있고 **예정·진행 중·기간 종료**를 구분합니다. 6월 15일에는 6월 1~14일 계획이 기간 종료로 남으며 카드의 **실행 관리 열기 / 결과 확인**으로 들어갑니다. 상세 화면의 **계획 목록**으로 돌아올 수 있습니다. 일부 매장의 조회 실패는 오류로 표시하며 계획이 없다는 안내로 바꾸지 않습니다.

저장한 실행 계획의 **결과 확인**에서 실행일·실행 내용·메모·가상/운영 자료 구분을 저장합니다. 홍보·주문 안내는 실행 전·후 결제/상품 주문 CSV 네 파일로 매출·결제·오후 2~5시·선택 메뉴를 집계합니다. 날짜별 결제/상품 매출과 기록된 영업일이 일치해야 집계하며 원본 파일 이름·SHA-256도 함께 저장합니다. 영업일 누락과 실제 휴무는 자동 구별하지 못하므로 전체 자료 여부는 확인이 필요합니다.

결과 화면의 **비교할 POS 메뉴명**과 하루 발주 결과의 **메뉴명**은 저장된 분석의 상품 목록을 입력란 바로 아래에서 선택합니다. 목록에 없는 기존 저장 값은 유지하며, 상품 자료가 없거나 다른 메뉴를 비교할 때는 직접 입력할 수 있습니다. 메뉴를 바꾸면 이전 집계는 다시 계산해야 합니다.

[6월 실행 후 시연 안내](demo/the-aewol-june-rehearsal/follow-up/README.md): 결과 단계에서만 기준일을 **2021-06-15**로 바꾸고 **5월 18~31일 ↔ 6월 1~14일**을 비교합니다. 각 12영업일, 매출 **6,619,000→6,968,000원**, 결제 **312→336건**, 김치찌개 **204→247인분·1,632,000→1,976,000원**, 오후 2~5시 **48→72건**입니다. 전후 변화는 가상 상황이며 실제 홍보 효과 검증이 아닙니다.

발주 결과는 **6월 5일 하루**, 저장된 예상 **20~24인분**, 가상 판매 **23인분**과 배정 재료의 남은 양을 기록합니다. 돼지고기 **0.2kg**, 기본육수 **1.1L** 등은 김치찌개 배정분만의 가정입니다. 예정량·추가 발주 모두 입고, 다른 메뉴 사용·폐기·이동 없음을 가정하며 전체 매장 재고나 폐기 감소 효과로 설명하지 않습니다. 리뷰 결과는 확인하지 않은 건수와 확인된 0건을 구별하고 실행 후 원문이 없으면 **자료 부족·추가 관찰 필요**를 표시합니다.

2026-11-18: 프런트엔드 빌드, 실제 파서 집계·금액/영업일 불일치 거부, 독립 CSV 검증이 통과했습니다. 로컬 PostgreSQL 임시 DB에서 새 결과 저장·재조회·수정·소유권과 마이그레이션 반복 실행을 검증했고 새 테스트 **3개**·자동 게시 종료 **2개**가 통과했습니다. 실제 컴포넌트의 분리된 로컬 UI 모형에서 390px 표·수정 저장/새로고침·하루 결과·후기 부족 안내를 확인했습니다. 자동화 파일 선택은 도구 중단으로 완료하지 못해 파서는 별도 실행했습니다. 실제 아이폰과 Railway의 새 결과 저장 리허설은 별도 확인 대상입니다.

## 앱 시연 기준일

로그인한 화면의 사이드바에서 접힌 **시연 기준일**을 펼친 뒤 **시연 기준일 설정** 또는 **날짜 변경 → 애월 시연 · 2021년 6월 1일 → 시연 날짜 적용**을 누릅니다. 모바일은 상단 **메뉴 열기** 안에서 같은 항목을 펼칩니다. 본문의 큰 날짜 배너는 표시하지 않습니다. 계정에 저장되므로 같은 계정의 PC·아이폰에서 새로고침하면 적용됩니다. **날짜 변경 → 실제 날짜로 돌아가기**로 해제합니다. 변경 전 입력 중인 내용은 먼저 저장합니다.

사이드바 배치는 로컬 PC와 390px 모바일 화면에서 기본 접힘·키보드 펼치기·설정창 열기·취소·메뉴 접기를 확인했습니다. 실제 날짜 복귀와 2021-06-01 재적용·새로고침 유지, 본문 배너 제거와 모바일 가로 넘침 없음도 확인했습니다. 프런트엔드 프로덕션 빌드가 통과했으며 실제 아이폰에서의 추가 검증은 포함하지 않았습니다.

계획 기본 시작일·진행 상태, POS 입력 달력, 결과 확인 가능 시점과 발주 비교 자료의 기준일에 적용합니다. 기존에 저장한 계획 날짜나 POS 파일을 변경하지 않으며 로그인·인증서·저장 시각은 실제 시간을 유지합니다. 실제 토스 주문 조회와 기상청 API의 제공 가능 기간도 실제 날짜를 사용합니다. 과거 날씨는 당시 관측 조건을 활용한 재현이며 당시 예보나 예측 성능 검증을 뜻하지 않습니다. 시연 중에는 실제 인스타그램 게시·예약을 차단합니다.

기존 로컬 DB에는 `migration-rehearsal-date.sql`을 적용합니다. Railway Web은 시작 스크립트에서 이 마이그레이션을 적용합니다.

2026년 11월 18일 로컬 PostgreSQL·브라우저에서 기준일 적용·새로고침 유지·실제 날짜 복귀를 확인했습니다. 6월 계획이 시연에서는 **진행 중**, 실제 날짜에서는 **기간 종료**로 바뀌었고, 기준일을 생략한 새 발주 계획은 **2021-06-01~14**로 저장되며 `createdAt`은 실제 **2026년**을 유지했습니다. 다른 계정은 설정되지 않았고 미로그인 변경은 **401**, 미래 날짜는 **400**, 시연 중 실제 인스타 게시 요청은 **409**였습니다. 6월 5일 예상 이력은 **대상일 대기**이며 당일 POS 실적을 노출하지 않았습니다. 과거 관측 기반 **13~28그릇·추가 준비량 2.5~10kg**과 PC·390px 모바일 설정창, 모바일 가로 넘침 없음을 확인했습니다. 기존 백엔드 테스트는 실패·오류 없이 완료됐고 3건은 기존 환경 조건으로 생략됐습니다. 프런트엔드 빌드와 Java 21 패키징도 통과했습니다. 실제 아이폰 조작은 이번 검증에 포함하지 않았습니다.

수요는 선택일·시연 기준일 이전 12주 안의 같은 요일 POS에서 확인합니다. 최근 6회가 있으면 앞 3회와 뒤 3회의 평균을 비교하고, 최종 범위는 **뒤 3회의 판매 수준을 한 번만 반영**합니다. 최근 평균에 감소율을 다시 곱하거나 월 매출 감소율로 판매 수량을 임의 차감하지 않습니다. 3~5회뿐이면 최근 최대 4회의 범위를 쓰고 추세 판단 부족을 안내하며, 3회 미만은 준비량 계산을 막습니다. 메뉴의 최근 판매가 0이면 0을 유지하고, 비교 기간 평균이 0일 때 증감률을 만들지 않습니다.

날씨는 같은 비교 기록에서 강수·비강수가 **각각 3회 이상**이고 앞·뒤 기간 모두 두 조건을 포함할 때만 참고합니다. 각 기간 평균으로 나눈 상대 판매를 비교해 추세와 날씨 차이가 섞이는 것을 줄이고 보정은 **0.8~1.2배**로 제한합니다. 관측 누락·표본 부족·두 조건을 구분할 수 없는 기간은 보정하지 않고 이유를 표시합니다. 결과는 최근 기록 기반의 준비 참고 범위이며 통계적 예측 신뢰구간이나 성능 검증값은 아닙니다.

발주 계획의 **점검표·완료 수·다음 할 일·실행 결과 확인**은 화면 위에서 스크롤을 따라갑니다. 점검표는 필요할 때 펼치며 직접 체크한 상태를 저장합니다. 기존 계획의 체크 여부·ID는 유지하고 과거 ‘다음 입고까지’ 안내를 하루 기준 표현으로 보여줍니다. 재료는 접힌 목록에서 하나씩 펼쳐 입력하고 닫힌 상태에서도 부족량을 확인합니다. 최종 추가 발주량은 빈칸이 미결정, 0이 추가 발주 없음이며 저장 후 결과 화면에 연결됩니다.

PC와 390px 모바일에서 스크롤 중 진행표 상단 고정, 접기·체크 저장·새로고침 유지, 재료 한 항목씩 펼치기와 결과 바로가기를 확인했습니다. 김치찌개는 월 매출 감소와 별개로 최근 같은 토요일 평균이 25→29.6667개여서 **28~32개**가 나왔습니다. 월 매출 감소를 일별 수량 감소로 간주하지 않습니다. 운영 자료 변경·실제 발주 주문·실제 아이폰 조작을 포함한 검증은 아닙니다.

## 기간을 비워둔 POS의 월별 검색

**매출 입력 → POS 파일 업로드 → 내 매장 월별 파일**에서 기준 월·비교 월을 고르면 파일 속 거래 날짜로 후보를 찾습니다. 내보내기 기간이 없거나 일부 기간으로 등록돼 있어도 해당 월 거래가 있으면 목록에 표시됩니다. 파일명만으로 월을 추정하지 않습니다.

파일마다 실제 거래 날짜 범위와 거래가 있는 일수, **월 전체 여부 확인 필요** 또는 **월 전체 기간 확인됨**을 표시합니다. 미확인 파일은 **이 파일은 … 전체 내역이에요. (휴무·무거래일 포함)**을 확인하면 해당 파일의 내보내기 기간으로 저장됩니다. 두 달 이상 묶인 파일은 표시된 전체 월 범위를 확인합니다. 재업로드나 새 CSV 생성 없이 기존 파일 ID·내용을 유지합니다. 이미 유효한 전체 기간이 저장돼 있으면 확인을 반복하지 않습니다.

두 달 결제 파일과 함께 선택한 상품 주문 파일의 전체 기간이 확인되면 자동 집계합니다. 상품 주문은 두 달 모두 선택·확인해야 포함되며 **이번 분석에서 제외**할 수도 있습니다. 파일이나 월을 바꾸면 기존 미리보기를 지우고 다시 검증합니다. 진행 중인 월은 월 전체 자료로 처리하지 않습니다. 토스 연동 파일의 기간은 토스포스 재조회로 갱신하며, 거래 날짜를 읽지 못한 파일은 오류를 안내합니다. 직접 수정할 때는 **파일 관리에서 기간 수정 → 전체 파일 → 기간 수정**으로 이동합니다.

2026년 11월 18일 별도 로컬 PostgreSQL과 브라우저에서 확인했습니다. 기간 없는 4·5월 결제·상품 주문 CSV 네 개가 각각 거래일 **26일**로 검색됐고, 미확인 상태에서 분석이 비활성화됐습니다. 네 파일 확인 후 **32,379,500원 → 29,581,000원**, 메뉴 **10개**가 집계됐고 새로고침 후에도 기간 확인이 유지됐습니다. 원래 네 파일의 ID와 내용 해시는 같았습니다. 미확인 하루 자료 선택 시 분석 차단, 두 달 묶음 결제 파일을 양쪽 월에 선택한 뒤 전체 범위를 확인해도 같은 금액 유지, 상품 주문 제외·복원과 실제 분석 저장을 확인했습니다. 390px 모바일에서 가로 넘침이 없었고 프런트엔드 프로덕션 빌드가 통과했습니다. 이 결과는 실제 아이폰 조작·운영 자료 변경을 포함하지 않습니다.

## 매장 삭제

**내 매장**에서 삭제할 매장을 선택하고 **매장 삭제**를 누릅니다. 확인창에서 매장명·주소와 삭제 범위를 확인한 뒤 **매장과 자료 삭제**를 누르면 POS 파일, 분석·질문 이력, 실행 계획·결과, 리뷰, 메뉴 사진·원가·재고 설정과 공개 QR 메뉴판이 함께 삭제됩니다. 삭제는 되돌릴 수 없고 기존 QR 주소도 닫힙니다. 다른 매장과 계정은 유지되며 이미 SNS에 게시된 홍보물은 외부 서비스에 남습니다.

예약·게시 중이거나 게시 여부 확인이 필요한 인스타그램 계획이 있으면 삭제를 막습니다. 실행 관리에서 예약을 취소하거나 게시 상태를 확인한 뒤 다시 삭제합니다. API는 로그인한 소유자에게만 허용하며 연결 자료 전체를 한 트랜잭션으로 처리합니다. DB 스키마 변경은 필요하지 않습니다.

2026년 11월 18일, 별도 로컬 PostgreSQL과 가상 계정으로 확인했습니다. 브라우저에서 매장명·주소와 삭제 범위가 표시되고 취소 시 매장이 유지됐습니다. API는 미로그인 401, 다른 소유자 404, 인스타그램 예약·게시 중·확인 필요 상태 각각 409를 반환했습니다. 자료 없는 매장과 연결 자료가 있는 매장 모두 삭제에 성공했고, 후자는 연관 자료 18개 테이블에 잔존 자료가 없었습니다. 공개 QR은 삭제 전 200에서 삭제 후 404로 바뀌었으며 다른 매장 2개와 계정 2개는 보존됐습니다. 프런트엔드 프로덕션 빌드와 Java 21 백엔드 패키징도 통과했습니다. 이 검증은 Railway 운영 자료를 사용하지 않았습니다.

2. 백엔드에 `SHOP_BUDDY_DB_URL`, `SHOP_BUDDY_DB_USER`, `SHOP_BUDDY_DB_PASSWORD`를 설정하고 Java 21에서 `mvn -f backend/pom.xml spring-boot:run`을 실행합니다.
3. 저장소 루트에서 `npm --prefix frontend ci`와 `npm --prefix frontend run dev`를 실행합니다. 프론트엔드 개발 서버는 `/api` 요청을 로컬 백엔드의 8080 포트로 전달합니다.

기존 개발용 DB에는 `migration-store-reviews.sql`을 다시 적용해 리뷰 분류 열을 추가합니다.
기존 개발용 DB에서 AI 추천을 실행 계획에 저장하려면 `migration-strategy-recommendations.sql`도 적용합니다.
실행 가이드 저장에는 위 파일 적용 후 `migration-execution-guide-snapshots.sql`을 적용합니다.
기존 개발용 DB에서 차트 질문 대화와 **새 질문**을 사용하려면 `migration-chart-questions.sql`을 적용합니다. **새 질문**을 누르면 현재 분석에서 빈 대화를 시작합니다.
기존 개발용 DB에서 분석 이름을 저장하려면 `migration-analysis-name.sql`을 적용합니다.
기존 개발용 DB에서 POS 품목별 판매량을 저장하려면 `migration-pos-product-sales.sql`을 적용합니다. 상품 주문의 판매가와 프로모션 입력값 불러오기를 사용하려면 품목별 판매량·프로모션 검토 마이그레이션 적용 후 `migration-promotion-input-defaults.sql`도 적용합니다.
기존 개발용 DB에서 발주 검토표를 저장하려면 `migration-inventory-review.sql`을 적용합니다.
기존 개발용 DB에서 매장별 메뉴 재료 사용량을 저장하려면 `migration-store-inventory-recipes.sql`을 적용합니다.
**내 매장 → 메뉴 재료·원가**를 사용하려면 기존 DB에 `migration-store-menu-costs.sql`을 적용합니다. 최초 입력 시 기존 발주 검토의 재료 사용량을 불러올 수 있으며, 저장한 뒤에는 발주 화면도 메뉴 재료·원가의 값을 사용합니다. 재료별 사용량과 단가를 곱한 뒤 합산액을 원 단위로 반올림해 저장합니다. 새 프로모션 검토에서 품목을 선택하면 저장된 메뉴 원가를 우선 불러오고, 이전에 저장한 프로모션 검토의 원가는 해당 계획에 보관됩니다.
**내 매장 → 손익분기점**을 사용하려면 이어서 `migration-store-break-even.sql`을 적용합니다. 월 임대료·고정 인건비·기타 고정비·영업일과 수수료 등 추가 변동비율을 저장할 수 있습니다. 최근 분석의 품목별 실판매금액이 전체 매출과 일치하고 판매된 품목의 원가가 모두 있으면 저장한 원가로 재료비율을 계산합니다. 예상 재료비율을 직접 입력할 수도 있습니다. 하루 목표 매출은 월 고정비를 공헌이익률과 영업일 수로 나눈 값을 올림한 결과입니다.
**내 매장 → 다국어 QR 메뉴판**을 사용하려면 기존 DB에 `migration-store-qr-menu.sql`을 적용합니다. 연결된 Python Agent는 영어·중국어 간체·일본어 메뉴명 초안을 제공합니다. 사장님이 확인하고 공개하면 최근 POS 판매가, 등록 사진, 확인한 번역이 손님용 링크에 반영됩니다. 손님은 로그인 없이 열 수 있고 공개 중지 시 링크와 사진이 닫힙니다. 손님용 주소가 관리 화면과 다를 때는 프런트엔드 실행 또는 빌드 전에 `VITE_PUBLIC_MENU_ORIGIN`에 손님이 접속할 수 있는 주소를 설정합니다.
메뉴 원가 화면의 **영수증에서 단가 읽기**는 기존 Python Agent의 OpenAI 이미지 입력을 사용합니다. Agent에 `STRATEGY_AI_API_KEY` 또는 `OPENAI_API_KEY`를 설정합니다. 필요하면 `RECEIPT_AI_MODEL`로 판독 모델을 바꿀 수 있습니다. 개인정보를 가린 JPG·PNG(최대 3MB)에서 읽은 항목은 구매량과 금액을 확인한 뒤 선택해 적용합니다. **재료·원가 저장**을 눌렀을 때 DB에 반영됩니다.
기존 개발용 DB에서 발주 예상 범위를 저장하려면 `migration-inventory-demand-snapshots.sql`을 적용합니다.
발주 검토에서 확인 메모를 저장하려면 `migration-inventory-demand-notes.sql`을 적용합니다. 같은 매장의 메뉴와 날짜에 저장한 메모는 다음 발주 계획의 예상 이력에서도 볼 수 있습니다.
발주 예상에서 비교 날짜를 제외하려면 기존 DB에 `migration-inventory-demand-exclusions.sql`을 적용합니다. **비교할 POS 날짜 선택**에서 판매량과 확인 메모를 보고 날짜를 제외하거나 다시 포함할 수 있습니다. 예상 범위를 저장하면 제외한 날짜도 함께 기록됩니다.
제외 전후 예상 범위를 함께 저장하려면 `migration-inventory-demand-original-bounds.sql`도 적용합니다. 발주 예상 이력에서 실제 판매량이 두 범위에 들어가는지 비교합니다. 범위를 벗어나면 실제 판매량과 가장 가까운 범위 경계의 차이를 비교합니다. 이전에 저장한 기록은 보관된 범위와 제외 날짜를 표시합니다.
기존 개발용 DB에서 프로모션 검토를 저장하려면 `migration-promotion-review.sql`을 적용합니다.
기존 개발용 DB에서 프로모션 홍보 초안과 메뉴 사진을 저장하려면 `migration-promotion-drafts.sql`을 적용합니다. 말투를 설정하지 않은 매장은 전략 Agent에 OpenAI가 연결되어 있으면 홍보 문구에 짧은 안내 문장을 추가합니다. 저장된 문구는 4번 화면에서 직접 편집할 수 있습니다.
기존 개발용 DB에서 매장 홍보 말투를 사용하려면 `migration-store-promotion-tone.sql`을 적용합니다. **내 매장 → 홍보 말투 설정**에서 기본 말투와 피하고 싶은 표현을 저장합니다.
기존 개발용 DB에서 매장별 POS 파일 보관을 사용하려면 `migration-store-pos-files.sql`을 적용합니다. **내 매장 → POS 파일 관리**에서 결제 내역 엑셀·CSV 또는 상품 주문 CSV를 저장하면 매출 입력에서 다시 선택할 수 있습니다.
POS 기록 달력과 행사 결과 자동 집계를 사용하려면 기존 DB에 `migration-pos-file-coverage.sql`도 적용합니다. **내 매장 → POS 파일 관리**에서 달력 날짜를 눌러 파일을 등록하거나 **전체 파일**에서 기록 월·파일 종류·파일명으로 찾을 수 있습니다. 달력 기록일과 실제 거래일은 따로 표시합니다. 종료된 홍보 계획은 로그인한 웹앱에서 보관된 상품 주문 POS를 찾아 비교합니다. 주문 없는 날을 포함한 전체 POS 내보내기 기간은 파일 저장 시 선택으로 기록할 수 있습니다. 상단 알림은 한국 시간 기준 주간 POS 등록과 결과 확인, 필요한 POS 기간을 안내합니다.

토스포스 주문·결제를 불러오려면 기존 DB에 `migration-toss-pos-import.sql`을 적용합니다. 백엔드에 `SHOP_BUDDY_TOSS_STORE_ID`(가게짝꿍 매장 UUID), `SHOP_BUDDY_TOSS_MERCHANT_ID`(토스 가맹점 ID), `SHOP_BUDDY_TOSS_ACCESS_KEY`, `SHOP_BUDDY_TOSS_ACCESS_SECRET`을 설정합니다. 연결한 매장의 **내 매장 → POS 파일 관리 → 토스포스에서 불러오기**에서 한 달씩 가져올 수 있습니다. 같은 달을 다시 불러오면 토스포스 결제·상품 주문 보관본을 갱신합니다. 이번 달 파일은 진행 중으로 표시하며, 월별 보관 POS 비교는 마감된 두 달의 파일을 사용합니다. 할인·환불 등을 품목별 금액으로 확정하기 어려운 주문은 수량만 기록합니다.

기존 개발용 DB에는 `migration-concern-product-revenue.sql`도 적용합니다. 새 분석을 저장할 때 POS 상품 주문의 실판매금액이 있으면 품목별 판매량과 함께 집계합니다. 실판매금액을 저장하기 전에 만든 분석은 해당 POS 상품 주문을 포함해 새로 저장하면 품목 매출액을 비교할 수 있습니다.

기존 개발용 DB에서 맞춤 홍보 계획을 사용하려면 `migration-custom-strategies.sql`, `migration-marketing-materials.sql` 순서로 적용합니다. 맞춤 홍보 전략은 할인 조건을 입력하지 않아도 실행 관리에서 메뉴나 가게 소식을 소개할 수 있습니다.

기존 개발용 DB에서 공개 후기 검색과 채널별 홍보를 사용하려면 위 맞춤 홍보 마이그레이션 이후 `migration-promotion-review-points.sql`을 적용합니다. 신규 DB의 `schema.sql`에는 이 변경이 포함돼 있습니다. Spring Boot에 연결된 Python Agent에 `STRATEGY_AI_API_KEY` 또는 `OPENAI_API_KEY`를 설정하면 공개 후기 검색과 채널별 문구 생성에 OpenAI를 사용합니다. 검색·문구 생성 모델은 각각 `PROMOTION_SEARCH_MODEL`, `PROMOTION_COPY_MODEL`로 바꿀 수 있습니다.

**4번 실행 관리 → 홍보물 만들기**에서 실행 기간과 겹치는 제주 행사를 선택하면 세 채널 문구에서 행사와 매장 메뉴를 이어 소개합니다. 미리보기에는 행사 일정, 장소, 출처도 표시됩니다. 게시일이 행사 종료일을 지나면 해당 행사는 선택할 수 없습니다. 목록에는 2021년 제주현대미술관 전시와 2026 제주감귤박람회 기록이 있습니다. 선택한 행사와 출처는 초안에 함께 저장됩니다.

3번 대응 전략 화면에 AI 추천을 표시하려면 [Python Agent](agent/README.md)를 먼저 실행하고, Spring Boot 실행 셸에서 `STRATEGY_AGENT_URL=http://127.0.0.1:8001`을 설정합니다. Agent 연결이 꺼져 있거나 응답을 사용할 수 없으면 같은 화면에 기본 추천을 표시합니다.

2번 매출 분석의 차트 질문도 같은 Agent를 사용합니다. 저장된 분석에서 질문하면 해당 분석의 대화를 PostgreSQL에 저장합니다. 새로고침하면 질문과 답변 당시의 근거가 복원됩니다. 공식 가이드가 필요하면 대응 전략 카드에서 가이드를 먼저 열어 두세요.
AI 추천으로 계획을 만들면 추천 이유, 매출·상권 근거와 제주 BSI가 선택 당시 값으로 저장되며, 4번 실행 관리 화면에서 다시 확인할 수 있습니다.

서버에 `REVIEW_AI_API_KEY`를 설정하면 새 리뷰 본문을 OpenAI에 보내 오후 주문 안내, 주차, 대기시간 불편을 분류합니다. `REVIEW_AI_MODEL`로 모델을 바꿀 수 있습니다. 키가 없거나 분류 요청이 실패하면 서버의 주제별 규칙을 사용합니다. 이전에 저장한 리뷰에도 규칙을 적용합니다.

기존 개발용 DB에서 5번 화면의 홍보 품목 POS 비교를 사용하려면 `migration-promotion-impact.sql`을 적용합니다. 채널별 직접 게시 기록을 사용하려면 맞춤 홍보 마이그레이션과 POS 비교 적용 후 `migration-manual-promotion-publication.sql`도 적용합니다. 일반 사용에서 **홍보물 보기 → 해당 채널 → 실제 게시일 기록**으로 직접 게시한 날짜를 저장할 수 있습니다. 과거 시연 모드에서는 실제 게시일 기록을 표시하지 않아 과거 행사와 오늘의 시연 게시를 섞지 않습니다. 5번 화면에서는 첫 게시일을 기준으로 행사 전후 POS를 한 번 비교합니다.

매장 주소 검색은 Spring Boot의 환경 변수로 설정합니다. **도로명·지번** 검색에는 네이버 Maps Geocoding의 `NAVER_MAPS_CLIENT_ID`와 `NAVER_MAPS_CLIENT_SECRET`이 필요합니다. **가게 이름** 검색에는 NAVER API HUB 지역 검색의 `NAVER_LOCAL_SEARCH_CLIENT_ID`와 `NAVER_LOCAL_SEARCH_CLIENT_SECRET`이 필요합니다. 각 값은 발급받은 키로 설정한 뒤 백엔드를 다시 실행합니다.

기존 개발용 DB에서 POS 시간대별 집계와 고민 확인을 사용하려면 `migration-concern-hourly-sales.sql`을 적용합니다. 고민 확인에는 위 Python Agent와 모델 설정이 필요합니다.

## Railway 배포와 동시 요청 검증

- **모바일 헤더** — **320px·390px·430px·550px**에서 로고와 오른쪽의 종·계정 버튼이 한 줄에 표시됐습니다. 계정은 동그란 **‘애’** 버튼으로 보였고, **320px**에서 알림 메뉴와 마이페이지 메뉴가 각각 열렸습니다. **768px·1366px**에서 계정 이름이 표시되는 것도 확인했습니다.

### 아이폰 주간 POS 자동 알림

- 기존 PostgreSQL에는 `migration-weekly-pos-push.sql`을 적용합니다. 서버에 `SHOP_BUDDY_WEB_PUSH_PUBLIC_KEY`, `SHOP_BUDDY_WEB_PUSH_PRIVATE_KEY`, `SHOP_BUDDY_WEB_PUSH_SUBJECT`를 설정합니다.

- 기본 발송 시각은 **매주 월요일 오전 9시(한국 시간)**입니다. `SHOP_BUDDY_WEEKLY_POS_DAY`와 `SHOP_BUDDY_WEEKLY_POS_TIME`으로 요일과 시각을 설정합니다. 구독이 켜진 계정마다 주간 발송 시도를 한 건만 기록합니다. 알림을 누르면 해당 매장의 지난주 일요일 POS 등록 화면이 열립니다. 매장이 여러 개면 최근 등록 매장을 엽니다.
- 로컬에서 즉시 확인하려면 `SHOP_BUDDY_WEEKLY_POS_TEST_STORE_ID`에 테스트 매장 UUID를 설정하고 `SHOP_BUDDY_WEEKLY_POS_TEST_DELAY_SECONDS`로 등록 후 대기 시간(기본 45초)을 지정합니다. 해당 매장 계정에 같은 자동 발송 경로가 실행되며, 한 주에 한 번만 보냅니다. 로컬 테스트 중에는 PC의 백엔드와 HTTPS 주소가 동작해야 합니다.

### 실행 결과와 POS 자료 요청 자동 알림

- 기존 DB에는 `migration-weekly-pos-push.sql` 적용 후 `migration-execution-result-push.sql`을 적용합니다. 아이폰 홈 화면 앱의 **종 → 실행 결과 알림 켜기**에서 수신을 선택합니다. 주간 POS 알림과 별도로 켜고 끌 수 있습니다.

### 기상청 강수 관측 재조회 검증

기상청 과거 강수 관측 요청이 타임아웃이나 서버 오류로 실패하면 자동으로 한 번 더 조회합니다. 과거 관측을 확인하지 못해 같은 요일의 판매 범위를 표시하는 경우, 발주 검토 화면에서 계산 기준을 설명하고 **예상 판매량 보기**로 다시 조회할 수 있다고 안내합니다.

2026년 11월 16일, 백엔드를 재시작한 뒤 로컬 브라우저 `5220`에서 별도 검증 계정에 복사한 자매국수 리허설용 POS로 **2021년 5월 29일 고기국수**를 조회했습니다. 첫 조회에서 기상청 강수 관측이 반영됐고, 같은 요일에 강수 여부가 같았던 **5일**을 비교해 예상 판매량 **17~24개**를 표시했습니다. 자동으로 불러온 한 그릇당 돼지고기 **0.5kg**에 현재 재고 **3kg**과 입고 예정 **1kg**을 입력하니 추가 준비량 **4.5~8kg**이 표시됐습니다.

자동 재조회는 모의 응답으로도 검증했습니다. 첫 요청의 HTTP 503 이후 관측값을 받아오는 경우, 두 번 모두 타임아웃이면 관측값 없이 반환하는 경우, HTTP 400이면 재조회 없이 반환하는 경우를 확인했습니다.

PR #97 머지 후 `main`(`692f138`)의 로컬 브라우저 `5220`에서 같은 자매국수 리허설용 POS로 재검증했습니다. **2021년 5월 29일 고기국수**를 처음 조회했을 때 기상청 강수 관측이 반영됐고, 같은 요일에 강수 여부가 같았던 5일을 비교한 예상 판매량은 **17~24개**였습니다. 자동으로 불러온 한 그릇당 돼지고기 **0.5kg**에 현재 재고 **3kg**과 입고 예정 **1kg**을 입력하니 추가 준비량은 **4.5~8kg**이었습니다.
