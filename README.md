# 가게짝꿍 · 제주 소상공인 매출 대응 AI Agent

## API 연동 로컬 실행

1. 빈 개발용 PostgreSQL 데이터베이스에 `schema.sql`, `migration-store-reviews.sql`, `seed-jeju-areas.sql`, `seed-aewol-demo.sql` 순서로 적용합니다. 마지막 파일은 가상 매장과 개발용 로그인 정보를 제공합니다.
2. 백엔드에 `SHOP_BUDDY_DB_URL`, `SHOP_BUDDY_DB_USER`, `SHOP_BUDDY_DB_PASSWORD`를 설정하고 Java 21에서 `mvn -f backend/pom.xml spring-boot:run`을 실행합니다.
3. 저장소 루트에서 `npm --prefix frontend ci`와 `npm --prefix frontend run dev`를 실행합니다. 프론트엔드 개발 서버는 `/api` 요청을 로컬 백엔드의 8080 포트로 전달합니다.

기존 개발용 DB에는 `migration-store-reviews.sql`을 다시 적용해 리뷰 분류 열을 추가합니다.
기존 개발용 DB에서 AI 추천을 실행 계획에 저장하려면 `migration-strategy-recommendations.sql`도 적용합니다.
실행 가이드 저장에는 위 파일 적용 후 `migration-execution-guide-snapshots.sql`을 적용합니다.
기존 개발용 DB에서 차트 질문 대화를 저장하려면 `migration-chart-questions.sql`을 적용합니다.
기존 개발용 DB에서 분석 이름을 저장하려면 `migration-analysis-name.sql`을 적용합니다.
기존 개발용 DB에서 POS 품목별 판매량을 저장하려면 `migration-pos-product-sales.sql`을 적용합니다. 상품 주문의 판매가와 프로모션 입력값 불러오기를 사용하려면 품목별 판매량·프로모션 검토 마이그레이션 적용 후 `migration-promotion-input-defaults.sql`도 적용합니다.
기존 개발용 DB에서 발주 검토표를 저장하려면 `migration-inventory-review.sql`을 적용합니다.
기존 개발용 DB에서 매장별 메뉴 재료 사용량을 저장하려면 `migration-store-inventory-recipes.sql`을 적용합니다.
**내 매장 → 메뉴 원가·마진**을 사용하려면 기존 DB에 `migration-store-menu-costs.sql`을 적용합니다. 메뉴 원가를 처음 입력할 때 발주 검토에 저장한 재료 사용량을 불러옵니다. 재료별 사용량과 단가를 곱한 뒤 합산액을 원 단위로 반올림해 저장합니다. 새 프로모션 검토에서 품목을 선택하면 저장된 메뉴 원가를 우선 불러오고, 이전에 저장한 프로모션 검토의 원가는 해당 계획에 보관됩니다.
**내 매장 → 손익분기점**을 사용하려면 이어서 `migration-store-break-even.sql`을 적용합니다. 월 임대료·고정 인건비·기타 고정비·영업일과 수수료 등 추가 변동비율을 저장할 수 있습니다. 최근 분석의 품목별 실판매금액이 전체 매출과 일치하고 판매된 품목의 원가가 모두 있으면 저장한 원가로 재료비율을 계산합니다. 예상 재료비율을 직접 입력할 수도 있습니다. 하루 목표 매출은 월 고정비를 공헌이익률과 영업일 수로 나눈 값을 올림한 결과입니다.
메뉴 원가 화면의 **영수증에서 단가 읽기**는 기존 Python Agent의 OpenAI 이미지 입력을 사용합니다. Agent에 `STRATEGY_AI_API_KEY` 또는 `OPENAI_API_KEY`를 설정합니다. 필요하면 `RECEIPT_AI_MODEL`로 판독 모델을 바꿀 수 있습니다. 개인정보를 가린 JPG·PNG(최대 3MB)에서 읽은 항목은 구매량과 금액을 확인한 뒤 선택해 적용합니다. 메뉴 원가 저장을 눌렀을 때 DB에 반영됩니다.
기존 개발용 DB에서 발주 예상 범위를 저장하려면 `migration-inventory-demand-snapshots.sql`을 적용합니다.
발주 검토에서 확인 메모를 저장하려면 `migration-inventory-demand-notes.sql`을 적용합니다. 같은 매장의 메뉴와 날짜에 저장한 메모는 다음 발주 계획의 예상 이력에서도 볼 수 있습니다.
발주 예상에서 비교 날짜를 제외하려면 기존 DB에 `migration-inventory-demand-exclusions.sql`을 적용합니다. **비교할 POS 날짜 선택**에서 판매량과 확인 메모를 보고 날짜를 제외하거나 다시 포함할 수 있습니다. 예상 범위를 저장하면 제외한 날짜도 함께 기록됩니다.
제외 전후 예상 범위를 함께 저장하려면 `migration-inventory-demand-original-bounds.sql`도 적용합니다. 발주 예상 이력에서 실제 판매량이 두 범위에 들어가는지 비교합니다. 범위를 벗어나면 실제 판매량과 가장 가까운 범위 경계의 차이를 비교합니다. 이전에 저장한 기록은 보관된 범위와 제외 날짜를 표시합니다.
기존 개발용 DB에서 프로모션 검토를 저장하려면 `migration-promotion-review.sql`을 적용합니다.
기존 개발용 DB에서 프로모션 홍보 초안과 메뉴 사진을 저장하려면 `migration-promotion-drafts.sql`을 적용합니다. 말투를 설정하지 않은 매장은 전략 Agent에 OpenAI가 연결되어 있으면 홍보 문구에 짧은 안내 문장을 추가합니다. 저장된 문구는 4번 화면에서 직접 편집할 수 있습니다.
기존 개발용 DB에서 매장 홍보 말투를 사용하려면 `migration-store-promotion-tone.sql`을 적용합니다. **내 매장 → 홍보 말투 설정**에서 기본 말투와 피하고 싶은 표현을 저장합니다.
기존 개발용 DB에서 매장별 POS 파일 보관을 사용하려면 `migration-store-pos-files.sql`을 적용합니다. **내 매장 → POS 파일 관리**에서 결제 내역 엑셀·CSV 또는 상품 주문 CSV를 저장하면 매출 입력에서 다시 선택할 수 있습니다.
POS 기록 달력과 행사 결과 자동 집계를 사용하려면 기존 DB에 `migration-pos-file-coverage.sql`도 적용합니다. **내 매장 → POS 파일 관리**에서 달력 날짜를 눌러 파일을 등록하거나 **전체 파일**에서 기록 월·파일 종류·파일명으로 찾을 수 있습니다. 달력 기록일과 실제 거래일은 따로 표시합니다. 종료된 홍보 계획은 로그인한 웹앱에서 보관된 상품 주문 POS를 찾아 비교합니다. 주문 없는 날을 포함한 전체 POS 내보내기 기간은 파일 저장 시 선택으로 기록할 수 있습니다. 상단 알림은 한국 시간 기준 주간 POS 등록과 결과 확인, 필요한 POS 기간을 안내합니다.

토스포스 주문·결제를 불러오려면 기존 DB에 `migration-toss-pos-import.sql`을 적용합니다. 백엔드에 `SHOP_BUDDY_TOSS_STORE_ID`(가게짝꿍 매장 UUID), `SHOP_BUDDY_TOSS_MERCHANT_ID`(토스 가맹점 ID), `SHOP_BUDDY_TOSS_ACCESS_KEY`, `SHOP_BUDDY_TOSS_ACCESS_SECRET`을 설정합니다. 연결한 매장의 **내 매장 → POS 파일 관리 → 토스포스에서 불러오기**에서 한 달씩 가져올 수 있습니다. 같은 달을 다시 불러오면 토스포스 결제·상품 주문 보관본을 갱신합니다. 이번 달 파일은 진행 중으로 표시하며, 월별 보관 POS 비교는 마감된 두 달의 파일을 사용합니다. 할인·환불 등을 품목별 금액으로 확정하기 어려운 주문은 수량만 기록합니다.

기존 개발용 DB에는 `migration-concern-product-revenue.sql`도 적용합니다. 새 분석을 저장할 때 POS 상품 주문의 실판매금액이 있으면 품목별 판매량과 함께 집계합니다. 실판매금액을 저장하기 전에 만든 분석은 해당 POS 상품 주문을 포함해 새로 저장하면 품목 매출액을 비교할 수 있습니다.

기존 개발용 DB에서 맞춤 홍보 계획을 사용하려면 `migration-custom-strategies.sql`, `migration-marketing-materials.sql` 순서로 적용합니다. 맞춤 홍보 전략은 할인 조건을 입력하지 않아도 실행 관리에서 메뉴나 가게 소식을 소개할 수 있습니다.

기존 개발용 DB에서 공개 후기 검색과 채널별 홍보를 사용하려면 위 맞춤 홍보 마이그레이션 이후 `migration-promotion-review-points.sql`을 적용합니다. 신규 DB의 `schema.sql`에는 이 변경이 포함돼 있습니다. Spring Boot에 연결된 Python Agent에 `STRATEGY_AI_API_KEY` 또는 `OPENAI_API_KEY`를 설정하면 공개 후기 검색과 채널별 문구 생성에 OpenAI를 사용합니다. 검색·문구 생성 모델은 각각 `PROMOTION_SEARCH_MODEL`, `PROMOTION_COPY_MODEL`로 바꿀 수 있습니다.

**4번 실행 관리 → 홍보물 만들기**에서 실행 기간과 겹치는 제주 행사를 선택하면 세 채널 문구에 행사명·일정·장소가 들어갑니다. 게시일이 행사 종료일을 지나면 해당 행사는 선택할 수 없습니다. 현재 행사 목록에는 공식 공지에서 확인한 2026 제주감귤박람회 한 건을 등록했습니다. 선택한 행사와 공식 출처는 초안에 함께 저장됩니다.

3번 대응 전략 화면에 AI 추천을 표시하려면 [Python Agent](agent/README.md)를 먼저 실행하고, Spring Boot 실행 셸에서 `STRATEGY_AGENT_URL=http://127.0.0.1:8001`을 설정합니다. Agent 연결이 꺼져 있거나 응답을 사용할 수 없으면 같은 화면에 기본 추천을 표시합니다.

2번 매출 분석의 차트 질문도 같은 Agent를 사용합니다. 저장된 분석에서 질문하면 해당 분석의 대화를 PostgreSQL에 저장합니다. 새로고침하면 질문과 답변 당시의 근거가 복원됩니다. 공식 가이드가 필요하면 대응 전략 카드에서 가이드를 먼저 열어 두세요.
AI 추천으로 계획을 만들면 추천 이유, 매출·상권 근거와 제주 BSI가 선택 당시 값으로 저장되며, 4번 실행 관리 화면에서 다시 확인할 수 있습니다.

서버에 `REVIEW_AI_API_KEY`를 설정하면 새 리뷰 본문을 OpenAI에 보내 오후 주문 안내, 주차, 대기시간 불편을 분류합니다. `REVIEW_AI_MODEL`로 모델을 바꿀 수 있습니다. 키가 없거나 분류 요청이 실패하면 서버의 주제별 규칙을 사용합니다. 이전에 저장한 리뷰에도 규칙을 적용합니다.

기존 개발용 DB에서 5번 화면의 홍보 품목 POS 비교를 사용하려면 `migration-promotion-impact.sql`을 적용합니다. 채널별 직접 게시 기록을 사용하려면 맞춤 홍보 마이그레이션과 POS 비교 적용 후 `migration-manual-promotion-publication.sql`도 적용합니다. **홍보물 보기 → 해당 채널 → 실제 게시일 기록**에서 각 채널의 날짜를 저장할 수 있습니다. 가게짝꿍에서 인스타그램 게시가 완료되면 게시 시각이 자동으로 반영됩니다. 5번 화면에서는 첫 게시일을 기준으로 행사 전후 POS를 한 번 비교합니다.

매장 주소 검색은 Spring Boot의 환경 변수로 설정합니다. **도로명·지번** 검색에는 네이버 Maps Geocoding의 `NAVER_MAPS_CLIENT_ID`와 `NAVER_MAPS_CLIENT_SECRET`이 필요합니다. **가게 이름** 검색에는 NAVER API HUB 지역 검색의 `NAVER_LOCAL_SEARCH_CLIENT_ID`와 `NAVER_LOCAL_SEARCH_CLIENT_SECRET`이 필요합니다. 각 값은 발급받은 키로 설정한 뒤 백엔드를 다시 실행합니다.

기존 개발용 DB에서 POS 시간대별 집계와 고민 확인을 사용하려면 `migration-concern-hourly-sales.sql`을 적용합니다. 고민 확인에는 위 Python Agent와 모델 설정이 필요합니다.

### 인스타그램 즉시·예약 게시 테스트 설정

기존 개발용 DB에는 `migration-instagram-publication.sql`, `migration-instagram-schedule.sql`을 순서대로 적용합니다. 4번 실행 관리에서 **홍보물 보기 → 인스타그램 → 게시 관리**를 열면 **게시 전 최종 미리보기**에서 저장한 이미지와 문구를 확인할 수 있습니다. 즉시 게시 버튼은 연결된 테스트 매장에 메뉴 사진이 포함된 미게시 초안이 있을 때 표시됩니다.

Spring Boot 실행 환경에 아래 값을 설정합니다.

| 환경 변수 | 설정값 |
| --- | --- |
| `SHOP_BUDDY_INSTAGRAM_ACCESS_TOKEN` | 게시 권한이 있는 Meta 테스트 계정 토큰 |
| `SHOP_BUDDY_INSTAGRAM_ACCOUNT_ID` | 테스트용 Instagram 프로페셔널 계정 ID |
| `SHOP_BUDDY_INSTAGRAM_USERNAME` | 테스트 계정 사용자 이름(`@` 제외) |
| `SHOP_BUDDY_INSTAGRAM_TEST_STORE_ID` | 게시를 허용할 가게짝꿍 테스트 매장 UUID |
| `SHOP_BUDDY_INSTAGRAM_IMAGE_BASE_URL` | Meta가 읽을 수 있는 HTTPS 호스트 주소 |

HTTPS 호스트는 `GET /instagram-media/{key}.jpg` 경로만 Spring Boot에 전달합니다. 애월 테스트에서는 이미지 전용 임시 HTTPS 프록시를 사용하고 검증 후 종료했습니다. 토큰은 백엔드 환경 변수로 관리합니다.

예약은 한국 시간으로 입력합니다. 예약이 실행되는 동안 Spring Boot와 이미지 제공용 HTTPS 경로가 동작해야 합니다. 게시 시작 전에는 4번 화면에서 예약을 취소할 수 있습니다.

## 전체 흐름 검증

개발용 계정으로 로그인하고 새 매장을 등록합니다. 월별 매출과 시간대별 결제 건수를 입력하면 분석 화면에서 저장한 값을 조회할 수 있습니다. 대응 전략의 추천 근거를 확인한 뒤 실행 계획을 생성하고 점검표 항목 하나를 완료합니다. 실행 전후 합계와 영업일 수를 입력해 결과를 저장하고, 새로고침 후 다시 로그인하여 완료 상태와 결과를 확인합니다.

애월 테스트 매장으로 위 흐름을 검증했습니다. 오후 2~5시 결제 건수 180건 → 90건을 근거로 주문 안내 점검이 추천됐습니다. 실행 결과 화면에는 하루 평균 매출 10만 원 → 15만 원(+50.00%), 하루 평균 결제 6건 → 8건(+33.33%)이 표시됐습니다. 매장부터 실행 결과까지 같은 식별자로 연결된 레코드를 PostgreSQL에서 확인했습니다.

### 토스포스 주문·결제 불러오기와 월별 분석 검증

### 아이폰 주간 POS 자동 알림

- 기존 PostgreSQL에는 `migration-weekly-pos-push.sql`을 적용합니다. 서버에 `SHOP_BUDDY_WEB_PUSH_PUBLIC_KEY`, `SHOP_BUDDY_WEB_PUSH_PRIVATE_KEY`, `SHOP_BUDDY_WEB_PUSH_SUBJECT`를 설정합니다.

- 로컬에서 즉시 확인하려면 `SHOP_BUDDY_WEEKLY_POS_TEST_STORE_ID`에 테스트 매장 UUID를 설정하고 `SHOP_BUDDY_WEEKLY_POS_TEST_DELAY_SECONDS`로 등록 후 대기 시간(기본 45초)을 지정합니다. 해당 매장 계정에 같은 자동 발송 경로가 실행되며, 한 주에 한 번만 보냅니다. 로컬 테스트 중에는 PC의 백엔드와 HTTPS 주소가 동작해야 합니다.

### 실행 결과와 POS 자료 요청 자동 알림

- 기존 DB에는 `migration-weekly-pos-push.sql` 적용 후 `migration-execution-result-push.sql`을 적용합니다. 아이폰 홈 화면 앱의 **종 → 실행 결과 알림 켜기**에서 수신을 선택합니다. 주간 POS 알림과 별도로 켜고 끌 수 있습니다.
- 수신을 켠 날 이후 종료된 계획을 서버가 한국 시간 기준으로 확인합니다. 홍보 계획의 상품 주문 POS가 충분하면 첫 게시일 기준 전후 판매량과 실판매금액을 저장한 뒤 **결과 준비 완료**를 보냅니다. 누르면 해당 계획의 실행 결과가 열립니다.
- 상품 주문 POS에 빠진 날짜가 있으면 **POS 자료 필요**에서 해당 날짜와 파일 종류가 선택된 등록 화면을 엽니다. 등록 화면에서 같은 계획의 결과로 돌아갈 수 있습니다. 같은 계획·비교 조건·누락 기간의 알림은 한 번씩만 보냅니다.
- 로컬 실기기 테스트는 `SHOP_BUDDY_RESULT_PUSH_TEST_PLAN_ID`로 종료된 시연 계획 한 건을 지정합니다. 테스트 서버에서 그 계획의 알림을 켜면 기본 45초 뒤 상태를 확인하며, `SHOP_BUDDY_RESULT_PUSH_TEST_DELAY_SECONDS`로 시간을 조절합니다.

로컬 PostgreSQL에서 브라우저 없이 상품 주문 파일을 읽어 고기국수 **12개 → 18개**, **102,000원 → 135,000원**을 저장했습니다. 두 발송 작업이 동시에 실행되는 테스트에서 자료 부족과 결과 준비 알림이 각각 한 번만 처리됐습니다. 로컬 HTTPS `5193` 크롬에서 모의 알림을 누르니 **2021-06-25~06-30 상품 주문 등록**과 **같은 자매국수 계획의 실행 결과**가 각각 열렸습니다.

2026년 11월 12일 로컬 HTTPS `5193`의 실제 아이폰에서도 확인했습니다. 앱을 닫고 잠근 상태에서 **POS 자료 필요**를 받아 누르자 자매국수의 **2021-06-25~06-30 상품 주문 등록** 화면이 열렸습니다. 시연용 CSV를 POS API로 등록하자 서버가 앱을 열지 않은 상태에서 비교 결과를 저장했습니다. 아이폰에서 **결과 준비 완료**를 받아 누르니 같은 계획에서 고기국수 **12개 → 18개**, **102,000원 → 135,000원**이 보였습니다. Apple이 두 알림을 각각 **20:15:20**, **20:17:21**(한국 시간)에 수락했고, DB에 자료 부족과 결과 준비 발송이 각각 한 건씩 `SENT`로 기록됐습니다. 크롬에서 결과가 새로고침 후에도 유지되는 것을 확인했습니다.
