# 더애월 가상 실행 결과 시연

기존 4·5월 시연 POS 이후의 흐름을 보여주는 **새로 만든 가상 자료**입니다. 더애월의 실제 매출·발주·공개 후기·홍보 성과가 아닙니다. 식당이 이 검증에 참여했다는 의미도 아닙니다.

## 준비 파일

- 실행 전: 상위 폴더의 `SIMULATED-2021-05-payment.csv`, `SIMULATED-2021-05-product.csv`를 그대로 사용합니다. 화면에서 **5월 18~31일**만 집계합니다.
- 실행 후: 이 폴더의 `SIMULATED-2021-06-01-14-payment.csv`, `SIMULATED-2021-06-01-14-product.csv`입니다.
- `SIMULATED-2021-06-05-kimchi-allocated-stock.csv`는 **재고 결과 수동 입력 참고표**입니다. POS 업로드 칸에 넣지 않습니다.
- `expected-results.json`은 집계 결과·가정·원본 파일 해시 확인용입니다. 앱에 업로드하지 않습니다.

두 기간 모두 화요일~다음다음 월요일의 14일 중 **일요일 휴무를 가정한 12영업일**입니다. 요일마다 두 번씩 영업한 구성입니다. 실제 매장 영업일을 확인한 자료는 아닙니다. 5개 메뉴 정상가는 기존 CSV와 같고 김치찌개는 **8,000원**입니다. 기존 4·5월 파일은 변경하지 않습니다.

| 비교 항목 | 5월 18~31일 | 6월 1~14일 |
|---|---:|---:|
| 영업일 | 12일 | 12일 |
| 매장 매출 | 6,619,000원 | 6,968,000원 |
| 전체 결제 | 312건 | 336건 |
| 오후 2~5시 결제 | 48건 | 72건 |
| 김치찌개 | 204인분 | 247인분 |
| 김치찌개 매출 | 1,632,000원 | 1,976,000원 |

시연을 위해 오후 주문을 일부 늘린 상황입니다. 전후 차이가 홍보·할인의 인과 효과라고 설명하지 않습니다. 이 CSV는 **정상가 홍보**에 맞췄으며, 7,000원 할인 행사를 실행한 실적이라고 재사용하지 않습니다.

## 홍보 이후 결과 확인

1. 앞 단계의 분석·발주·후기·홍보·QR 확인이 끝난 뒤에만 **사이드바 → 시연 기준일 → 2021-06-15 → 저장**으로 바꿉니다. 새로운 분석을 만들거나 기존 4·5월 매출을 삭제할 필요는 없습니다.
2. 사이드바의 **실행 관리**를 누르면 저장된 계획 목록이 나옵니다. **더애월 본점 → 대표 메뉴와 가게 소식 홍보하기** 카드의 **결과 확인**을 누릅니다. 6월 15일에는 **기간 종료**로 표시되며 삭제된 것이 아닙니다. 새로고침해도 목록을 다시 불러옵니다. 실행 내용을 먼저 확인하려면 **실행 관리 열기**를 누른 뒤 위쪽 **결과 확인**으로 이동합니다.
3. **자료 구분: 가상 시연 자료**, 실행한 날짜 **2021-06-01**, 실행 내용 **가상 홍보 초안 검토 및 오후 안내 실행**을 적습니다. 메모에 **가상 운영 기록이며 실제 게시·성과 아님**을 남깁니다. 사용자가 오늘 시연 계정에 직접 게시한 사실이 있으면 오늘의 게시 사실과 2021년의 가상 실행을 구분합니다.
4. **POS로 실행 전·후 비교하기**를 펼칩니다. 메뉴명 **김치찌개**, 전 기간 **2021-05-18~31**, 후 기간 **2021-06-01~14**를 확인합니다. 계획의 시작일이 다르면 이 기간을 직접 지정합니다.
5. 실행 전 **결제 CSV·상품 주문 CSV**에 기존 5월 두 파일, 실행 후 두 칸에 이 폴더의 6월 두 파일을 넣습니다. 두 기간의 전체 영업 자료·요일·영업시간 확인란에 체크하고 **선택한 CSV로 집계하기**를 누릅니다.
6. 위 표 수치와 **하루 평균 매출 551,583→580,667원**, **하루 평균 결제 26→28건**을 확인합니다. 금액 평균은 원 단위 반올림 표시입니다.
7. **실행 기록과 결과 저장**을 누릅니다. 새로고침한 뒤 가상 표시·기간·집계·출처가 유지되는지 봅니다. **집계 출처와 파일 확인값**에는 네 파일 이름과 SHA-256이 나옵니다.

이 화면은 브라우저에서 파일을 읽어 집계와 파일 확인값을 서버에 저장합니다. CSV 원본을 매장 파일 보관함에 추가하는 기능과는 별개입니다. 날짜별 결제·상품 매출이 맞지 않거나 기록된 영업일이 다른 파일은 집계하지 않습니다. 파일에 기록이 없는 날이 휴무인지 누락인지는 자동 판별할 수 없어 원본 범위 확인이 필요합니다.

## 6월 5일 하루 발주 결과

1. 저장한 **발주량 검토하기** 계획의 **결과 확인**을 엽니다. 자료 구분은 **가상 시연 자료**로 둡니다.
2. 실행한 날짜와 발주를 검토한 하루 모두 **2021-06-05**, 메뉴 **김치찌개**를 입력합니다. 실행 내용은 **가상 김치찌개 배정 재료 하루 점검**으로 적습니다.
3. **하루 상품 주문 CSV로 판매량 채우기**에 6월 상품 주문 파일을 넣습니다. 이 날짜의 **23인분**만 집계합니다. 같은 계획에 저장한 예상 **20~24인분**이 표시되는지도 확인합니다. 저장한 예상이 없다면 없는 상태로 표시하며 수치를 만들어내지 않습니다.
4. **품목별 남은 재고 입력**을 펼쳐 아래 값으로 입력하고 저장합니다. 이 표는 김치찌개에 배정한 재료만 다룹니다. 메모에 **기존 예정량과 추가 발주 모두 당일 입고, 다른 메뉴 사용·폐기·이동 없음 가정**을 반드시 적습니다.

| 품목 | 남은 배정 재고 |
|---|---:|
| 돼지고기(원육) | 0.2kg |
| 김치 | 0.55kg |
| 두부 | 0.16kg |
| 양파 | 0.11kg |
| 완성 기본육수 | 1.1L |
| 쌀 | 0.43kg |
| 기본 반찬 | 2인분 |
| 찌개 양념 | 2인분 |

현재 재고 + 기존 예정 입고 + 추가 발주 입고 − 23인분 사용량으로 맞춘 가정입니다. 화면은 남은 재고를 기록하며 자동으로 폐기량이나 절감액으로 바꾸지 않습니다. 두루치기·꽁치찌개 등 다른 메뉴에도 재료를 사용했다면 이 배정 재고 계산을 전체 매장 재고로 설명하면 안 됩니다. 기존에 입력한 1.1L 같은 값은 이 결과표에 다시 기록해야 서버에 저장됩니다.

## 주문 안내·리뷰의 후속 확인

- 주문 안내 계획이 있으면 **결과 확인**에서 실제로 점검한 안내·실행 날짜·관찰 범위를 적습니다. 전후 POS를 넣지 않으면 **비교 POS 없음**으로 남깁니다. 같은 POS 변화를 여러 계획에서 보더라도 각 전략이 각각 매출을 올렸다고 설명하지 않습니다.
- 리뷰 관련 계획이 있으면 실행 후 후기 수와 확인 기간·원문 출처를 기록할 수 있습니다. 이번 과거 시연에는 새 실제 후기를 확보하지 않았으므로 **건수는 비워 두고**, 메모에 **실행 후 실제 후기 원문 없음**을 적습니다. 결과는 **자료 부족·추가 관찰 필요**입니다.
- 확인하지 않은 상태를 0건이라고 쓰지 않습니다. 실제로 0건임을 확인한 경우에만 검색 기간·출처와 함께 0을 적습니다. 후기가 있어도 불편 해소는 추가 관찰이 필요합니다. 시연을 위해 식당의 가짜 불만 후기·칭찬 후기를 만들지 않습니다.
- 리뷰 계획이 없다면 실제 근거 없이 새 불만 사례를 꾸며 만들지 않고 위 한계를 설명합니다.

## 검증 기록

2026-11-18: 독립 Python 검증과 실제 프런트엔드 파서가 위 전후 집계·6월 5일 23인분·재료 수지를 확인했습니다. 프런트 파서는 금액 불일치와 영업일 불일치를 거부했습니다. 로컬 PostgreSQL 임시 DB에서 저장·다시 불러오기·수정·다른 계정 접근 차단, 마이그레이션 반복 실행을 확인했습니다. 새 결과 API 3개와 기존 자동 게시 종료 2개 테스트가 통과했습니다. 배포 확인 중 발견한 인증 경로 누락을 수정하고 실제 Spring 보안 필터를 거친 HTTP 요청의 미로그인 401·로그인 후 조회/저장 200도 검증했습니다.

실제 컴포넌트의 로컬 UI 전용 서버에서 390px 결과 표, 실행 기록 수정·저장·새로고침, 하루 예상/판매·재고 표시, 리뷰 근거 부족 안내를 확인했습니다. 이 UI 서버는 운영 데이터와 분리한 모형 API이며 PostgreSQL 검증과는 별개입니다. 브라우저 자동화의 파일 선택 단계는 도구가 중단되어 완료하지 못했고, 파일 집계 로직은 실제 프런트 파서로 별도 검증했습니다. **실제 아이폰과 Railway의 새 결과 저장 리허설은 사용자가 이 순서대로 확인할 항목**입니다.
