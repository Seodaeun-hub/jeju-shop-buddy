# 가게짝꿍 최종 촬영 순서 · PC + 아이폰

서비스: [gage-jjakkung.up.railway.app](https://gage-jjakkung.up.railway.app/). 촬영 자료 ZIP을 **먼저 압축 해제**하고 아래 번호 폴더를 순서대로 사용합니다. 계정 비밀번호·API 키는 영상과 문서에 표시하지 않습니다.

대상은 **더애월 본점 공개정보를 참고한 2021년 가상 운영 사례**입니다. 현재 매장 운영 성과나 식당의 참여를 입증하는 시연이 아닙니다. 개인 참가로 정리했으며 팀 전환 작업은 남은 항목에서 제외합니다.

## 촬영 전 준비

- PC는 가로 화면, 아이폰은 세로 화면으로 각각 녹화하고 편집에서 이어 붙입니다. 아래 8~10분은 권장 편집 분량이며 대회가 정한 영상 길이가 아닙니다.
- PC·아이폰에서 같은 새 HTTPS 주소로 로그인합니다. 이전 Railway 주소의 로그인 상태는 자동 이전되지 않습니다. 로그인 입력·권한 승인·알림 팝업은 본 촬영 전에 정리합니다.
- 첫 장면의 시연 기준일은 **2021-06-01**입니다. 현재 저장 상태가 6월 15일이라면 사이드바 **시연 기준일 → 날짜 변경 → 2021-06-01 적용**으로 돌립니다. 실행 결과를 보여줄 때만 6월 15일로 바꿉니다. PC 날짜는 바꾸지 않습니다.
- 기존 매장·분석·사진·계획을 삭제하지 않습니다. 이미 등록된 파일은 재사용합니다. 새로 업로드하는 장면이 꼭 필요하면 별도의 촬영용 매장/계정에서 진행하고, 기존 화면을 새 업로드 성공 장면처럼 편집하지 않습니다.
- 메뉴 사진 5장·재료·원가는 미리 입력해 둡니다. 영상에서는 김치찌개 한 항목을 펼쳐 **8,000원·재료 8개·원가 3,100원**만 설명하고 긴 입력 과정은 줄입니다.
- 한 번 끝까지 연습한 뒤 녹화합니다. AI·외부 검색 대기는 편집으로 줄일 수 있지만, 실패를 성공한 것처럼 연결하거나 다른 자료의 답변을 붙이지 않습니다.

첫 설명: “제주데이터허브의 실제 상권 자료와 더애월 공개정보를 바탕으로 가상 POS를 만들었습니다. 상권과 매장의 차이를 찾고 발주·홍보를 준비한 뒤 결과를 확인하는 과정을 보여드리겠습니다.”

## 화면별 설명 멘트

다음 문장을 기본으로 읽되 화면에 실제로 표시된 내용을 기준으로 설명합니다. AI 답변 문장 자체를 외우지 않고 숫자·기간·출처를 확인합니다.

### PC01 · 홈에서 서비스 소개

홈의 말풍선과 그 아래 기능 소개를 천천히 스크롤합니다. 애니메이션 전체를 길게 보여주기보다 단계가 연결되는 모습을 남깁니다.

> 가게짝꿍은 제주 소상공인이 매출 변화를 살펴보고, 발주와 홍보를 준비한 뒤 실행 결과까지 확인하는 서비스입니다.

### PC02 · 매장과 시연 자료

더애월 본점의 지역·업종, POS 파일 네 개, 4·5월 선택과 분석 화면으로 넘어가는 장면을 찍습니다. 이미 저장된 자료는 불러오며, 새 업로드를 했다고 설명하지 않습니다.

> 제주데이터허브의 실제 상권 자료와 더애월 공개정보를 참고했습니다. 매장 POS와 재고, 실행 결과는 시연을 위해 만든 가상 자료이며, 2021년 6월의 운영 상황을 재현했습니다.

### PC03 · 매장 매출과 상권 비교

두 매출 막대와 상권 증감률을 보여주고 **참고 금액과 출처 보기**를 펼칩니다.

> 매장 매출은 약 1,634만 원에서 1,451만 원으로 11.23% 줄었습니다. 반면 같은 기간 애월읍 한식 업종의 카드 이용액은 7.34% 늘었습니다. 상권 전체 흐름과 다른 매장 내부의 변화를 살펴보겠습니다.

### PC04 · AI 질문과 근거

질문은 **“매출이 가장 많이 줄어든 메뉴와 결제가 줄어든 시간대를 근거와 함께 알려줘.”**로 입력합니다. 메뉴명을 먼저 알려주지 않고, 응답 뒤 **근거와 출처 보기**를 엽니다.

> 메뉴 이름을 지정하지 않고, 가장 많이 줄어든 메뉴와 시간대를 물어보겠습니다. 김치찌개는 610인분에서 462인분으로, 오후 2~5시 결제는 208건에서 104건으로 줄었습니다. 답변과 함께 집계 근거도 확인할 수 있습니다.

메뉴 판매량과 시간대 결제는 별도 집계입니다. 오후에 줄어든 주문이 모두 김치찌개였다고 단정하지 않습니다.

### IP01 · 아이폰 음성 입력

같은 분석의 질문창에서 **마이크 → 말하기 → 중지 → 문장 수정 → 보내기**를 찍습니다. 말할 질문은 PC04와 같아도 됩니다. 전사된 문장 끝에 “출처도 보여줘”를 직접 덧붙이는 등 수정 장면을 남깁니다. 수정 후 보내기를 누르고 답변까지 확인합니다.

> 휴대폰에서는 말로 질문할 수 있습니다. 인식된 문장을 확인하고 수정한 뒤, 보내기를 눌렀을 때만 전송됩니다.

아이폰은 중지 후 문장이 들어오는 방식입니다. 한 글자씩 실시간으로 입력되거나 자동 전송되는 기능으로 설명하지 않습니다.

### PC05 · 재료·원가와 하루 발주

김치찌개 **8,000원·재료 8개·원가 3,100원**을 잠깐 보여주고 발주 계획으로 이동합니다. **2021-06-05·김치찌개**의 예상 범위, 재고·기존 입고·추가 준비량을 확인합니다. **예상 범위 저장**과 **발주 검토표 저장**을 각각 남깁니다. 자세한 입력값은 아래 3절 표를 사용합니다.

> 메뉴별 재료 사용량과 원가는 미리 저장해 둡니다. 최근 같은 요일 판매량과 판매 추세를 바탕으로 예상 범위를 확인하고, 현재 재고와 기존 입고량을 제외해 추가 준비량을 계산합니다. 이번 조건에서는 20~24인분, 돼지고기는 0.5~0.9kg을 더 준비하는 것으로 나옵니다. 최종 수량은 사장님이 확인합니다.

날씨는 자료가 충분할 때 참고합니다. 화면에서 보정을 생략했다고 나오면 날씨가 반영된 결과라고 설명하지 않습니다. 외부 발주 주문은 전송하지 않습니다.

### PC06 · 실제 후기에서 홍보 초안까지

**대표 메뉴와 가게 소식 홍보하기**에서 김치찌개 후기를 찾고 날짜·원문·선택한 포인트를 보여줍니다. 당시 전시 정보와 사진을 선택해 세 채널 초안을 만들고, 문구와 출처를 확인합니다. 정상가 **8,000원**, 할인 없는 시연입니다.

> 시연 기준일 이전의 실제 공개 후기를 찾아 메뉴 특징을 확인합니다. 확인한 포인트와 당시 지역 전시 정보를 참고해 인스타그램, 네이버 플레이스, 당근용 초안을 만듭니다. 게시 전에는 사장님이 문구와 출처를 검토합니다.

외부 조회가 실패해 저장된 초안을 보여줄 때는 **사전 저장 초안 재생** 자막을 넣습니다. 실제 재검색 성공 장면처럼 연결하지 않습니다.

### IP02 · 모바일에서 홍보물 사용

PC와 같은 홍보 계획을 열어 **세 채널 탭 → 문구 복사 → 이미지 저장**을 찍습니다. 게시까지 찍는다면 아래 4절의 시연 계정·표시 문구를 따릅니다.

> 준비한 홍보물은 휴대폰에서도 확인할 수 있습니다. 채널에 맞는 문구를 복사하고 이미지를 저장해, 사용하는 앱에서 직접 게시합니다.

### IP03 · 로그인 없는 다국어 QR 메뉴판

PC에서 **내 매장 → 다국어 QR 메뉴판**의 실제 공개 QR을 띄우고, 아이폰으로 스캔합니다. Safari에서 한국어·English·简体中文·日本語를 전환하며 사진과 가격을 보여줍니다. 스캔 순간은 별도 카메라로 PC와 아이폰을 함께 짧게 찍고, 이후는 아이폰 화면 녹화를 사용해도 됩니다.

> 손님은 로그인 없이 QR로 메뉴판을 열 수 있습니다. 한국어·영어·중국어·일본어로 메뉴와 가격을 확인할 수 있어 외국인 손님 안내에도 활용할 수 있습니다.

### PC07 · 실행 전후 결과

**시연 기준일을 2021-06-15로 바꾸는 장면**을 먼저 남깁니다. 홍보 결과의 전후 기간·집계와 발주 결과의 예상·판매·남은 재고를 보여줍니다. 이미 저장했다면 결과를 열어 설명하고, 새로 입력하는 장면은 필요할 때만 찍습니다.

> 이제 대응 기간이 지난 상황으로 이동하겠습니다. 같은 길이의 전후 기간을 비교하면 김치찌개는 204인분에서 247인분으로, 오후 결제는 48건에서 72건으로 집계됩니다. 발주에서는 예상 20~24인분과 가상 POS에 기록된 판매 23인분을 함께 확인합니다. 이 결과는 기능을 보여주기 위한 가상 운영 자료입니다.

실제 식당의 판매나 홍보로 인한 매출 개선을 검증한 결과로 소개하지 않습니다.

### PC08 · 대응 흐름으로 마무리

**대응 한눈에 보기 → 흐름 재생**에서 분석 근거부터 발주·홍보·결과까지 연결되는 모습을 보여줍니다.

> 가게짝꿍은 상권과 매장 자료를 비교하고, 확인한 근거를 발주와 홍보로 연결합니다. 실행 후에는 결과를 기록해 다음 판단에 참고합니다. AI가 근거와 초안을 준비하고, 최종 실행은 사장님이 결정합니다.

## 실제 촬영 순서 · PC와 아이폰을 따로 녹화

편집 순서대로 기기를 계속 바꾸지 않고 **PC를 먼저 전부 촬영한 뒤 아이폰을 촬영**합니다. 멘트는 동시에 녹음하거나 편집할 때 별도로 녹음해도 됩니다. 한 장면씩 나눠 저장하면 다시 찍을 때 편합니다.

### PC 촬영

1. 시작 기준일 **2021-06-01**을 확인합니다.
2. **PC01 → PC02 → PC03 → PC04 → PC05 → PC06** 순서로 찍습니다.
3. 기준일을 **2021-06-15**로 바꾸는 장면을 포함해 **PC07 → PC08**을 찍습니다.
4. 아이폰 촬영 전에 기준일을 다시 **2021-06-01**로 돌립니다. 같은 계정의 PC·아이폰에 반영되는 설정이므로 두 화면에서 확인하고 새로고침합니다.

### 아이폰 촬영

1. 알림이 녹화에 들어오지 않도록 준비하고 Safari에서 같은 서비스에 로그인합니다. 마이크 권한은 본 촬영 전에 확인합니다.
2. **IP01**: 같은 매출 분석에서 음성 입력·중지·수정·전송·답변을 찍습니다.
3. **IP02**: 같은 홍보 계획에서 세 채널 확인·복사·이미지 저장을 찍습니다.
4. **IP03**: PC의 실제 공개 QR을 스캔하고 메뉴판 네 언어를 찍습니다. 로그인 없는 손님 화면임을 보여주려면 기존 로그인 탭과 별도의 비로그인 브라우저에서 엽니다.
5. 전체 흐름을 다시 확인할 때만 기준일을 6월 15일로 바꿉니다. 날짜가 다른 장면을 섞어 설명하지 않습니다.

**실행 관리 → 발주량 검토하기 → 결과 확인**에서 자료 구분 **가상 시연 자료**, 실행 날짜·발주 검토한 하루 모두 **2021-06-05**, 메뉴 **김치찌개**를 고릅니다. 실행 내용 **가상 김치찌개 배정 재료 하루 점검**을 적습니다.

**03_발주결과_하루판매/업로드용**의 6월 상품 주문 CSV를 **하루 상품 주문 CSV로 판매량 채우기**에 넣습니다. **6월 5일 판매23인분 / 저장 예상20~24인분**을 확인합니다. ‘저장한 예상 자료 없음’이면 원래 같은 발주 계획에서 6/5 김치찌개의 **예상 범위 저장**을 먼저 하고 돌아와 새로고침합니다.

남은 재고는 **돼지고기0.2kg, 김치0.55kg, 두부0.16kg, 양파0.11kg, 육수1.1L, 쌀0.43kg, 반찬2인분, 양념2인분**을 입력합니다. 메모: “김치찌개 배정 재료 기준. 기존 예정량과 추가 발주 모두 당일 입고, 다른 메뉴 사용·폐기·이동 없음 가정.” **실행 기록과 결과 저장** 후 재조회합니다. `입력참고용` CSV는 이 값을 보는 표이며 파일 선택칸에 올리지 않습니다.

마지막은 **대응 한눈에 보기 → 흐름 재생**입니다. 실제 상권 → 가상 매장 감소 → 사장님 확인 → 발주·홍보 → 가상 결과를 연결합니다. 주문 안내·리뷰 실행 결과 입력은 본편에서 생략합니다.

마지막 설명: “AI가 근거를 정리하고 사장님이 수량과 홍보 문구를 확인합니다. 현재 영상의 실행 결과는 가상 자료이며 실제 매장 매출 개선이나 인과 효과를 검증한 것은 아닙니다.”
